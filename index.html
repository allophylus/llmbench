The A3B 256K standard cell is measured, not pending: a 29,963-token calibrated prompt at a 256K server window gives 2,480.1 t/s prefill and 98.19 t/s decode (VRAM 24.83 → 24.89 GiB). Error bars are in the section below — every measured spread was under 5%. Rows whose weights are no longer on this machine say so in the Speed evidence column instead of showing a number that looks reproducible.

Two different speed measurements sit side by side and are never merged. @ 30K (group A) is the standardised probe: one cold request on a calibrated ~30K-token prompt, server rows only. Native ctx (groups B/C) is one probe at that row's own server context — group B shows the deepest depth probe (with @tokens), group C the llama-bench pp512/tg128 pair at the row's own context. A row with no 30K probe shows •n in group B and its rate in group C: it is a different measurement, not a restatement. pending means the standard probe is scheduled at that server context but has not been run yet.

Coverage: accuracy stops at 110K, speed reaches 256K

Accuracy cells (GPQA, AIME, LiveBench, ctx30k, ctx110k, tau2, Shell, TermBench) are measured up to a 110K embedded context. Speed rows reach the full 256K server window — the A3B rows show the standard 30K prompt at both 32K and 256K, plus deep probes out to 260K tokens. A blank accuracy cell above 110K means not measured, not failed: a 256K accuracy run costs ~2 minutes of prefill per question and is not part of the routine matrix. About this table

Every row is folded from one or more raw SCHEMA-1 run records produced by the benchmark suite; the per-row JSON files under raw/ are copies of the originals. Cells are percent correct on frozen prompt sets. The Decode / Prefill columns are pp512 (prefill) and tg128 (decode) tokens/s from llama-bench; the Server ctx / speed columns come from a live server: a cold request at temperature 0, cache_prompt:false, reading the server's own prompt_per_second and predicted_per_second. VRAM is the GPU's used-memory peak during the request. Videos are served from a CDN and only appear when the render exists. Every number here can be checked against the machine-readable dataset (data/results.json, plus the per-question chat JSONs); how each family of numbers is produced is on the method page.
