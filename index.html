Coverage: speed reaches 256K, accuracy stops at 110K

Accuracy cells (GPQA, AIME, LiveBench, ctx30k, ctx110k, tau2, Shell, TermBench) are measured up to a 110K embedded context. Speed rows reach the full 256K server window — the A3B rows show the standard 30K prompt at both 32K and 256K, plus deep probes out to 260K tokens. The matrix below does the same for every model: one row per model, with the server restarted at each of 4K, 32K, 64K, 128K and 256K and the prompt calibrated to that rung, so the columns are matched on both sides. A blank accuracy cell above 110K means not measured, not failed: a 256K accuracy run costs ~2 minutes of prefill per question and is not part of the routine matrix. How everything is produced is on the method page.

Speed by context — matched server context and prompt length

One model per row, five contexts across: 4K, 32K, 64K, 128K, 256K. Each cell is prefill t/s (how fast the prompt is ingested) over decode t/s (generation speed once the model answers). Server context and prompt length are matched in every cell — a 4K cell really is a 4K server serving a ~3.6K-token prompt, and 256K is a 256K server serving a ~256K prompt, on the same 32 GiB card. These are separate, matched-context measurements, not a restatement of the per-row probes above, and the two should not be quoted side by side.

How the context sweep was measured
  • Matched by construction. For each cell the server is stopped, restarted with -c <ctx>, and one prompt is built and calibrated with the model's own /tokenize to ctx − 512 tokens before it is sent. The 512-token headroom leaves room for the reply.
  • One cold request per cell. Temperature 0, top-k 1, prompt cache disabled, no streaming, a 64-token cap. The same request is used for every model and rung, so the columns are comparable down and across the table.
  • Validity checks, per cell. The context reported by the live server equals the rung; the -c argument is read back from the running process; the prompt lands within 0.2 percent of the target; the reply stops at the 64-token cap (finish reason length) — i.e. the model really did generate, not answer in two tokens.
  • GPU state. Every other model server is stopped before a cell and device memory is sampled at 1 Hz; the peak covers weights, caches for that rung, and the reply.
  • Failures are recorded, never substituted. Cells that did not measure are printed as such.
  • Read the columns as a curve, not a leaderboard. Part of the run shared the card with another job, so absolute prefill rates carry roughly ±5 percent extra noise; rung-to-rung ratios within a row are the reliable signal. Decode degrades with context on every model, but the size of the drop is a property of the model and its cache settings.

Source: benchmarks/ctx-sweep/ in the source repo — one JSON per model plus a combined sweep file, all cells checked in. Measured 2026-11-03. Rendered from those files by scripts/sweep_data.py.

About this table

Every row is folded from one or more raw SCHEMA-1 run records produced by the benchmark suite; the per-row records (raw records) are downloadable copies of the originals. Cells are percent correct on frozen prompt sets. The Decode / Prefill columns are pp512 (prefill) and tg128 (decode) tokens/s from llama-bench; the Server ctx / speed columns come from a live server: a cold request at temperature 0, cache_prompt:false, reading the server's own prompt_per_second and predicted_per_second. VRAM is the GPU's used-memory peak during the request. Videos are served from a CDN and only appear when the render exists. Every number here can be checked against the machine-readable dataset (data/results.json, plus the per-question chat JSONs); how each family of numbers is produced is on the method page.
