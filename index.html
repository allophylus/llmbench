Long-context prefill and the cache

Cache verdict: the 566 t/s at 260K is genuine cold prefill. Re-measured on the same long-context model with a 257,190-token prompt, one cold request per run and cache_prompt:false: 570.8 t/s with cache reuse on, 571.1 t/s with cache reuse off — a spread of 0.1%, inside run-to-run noise. A single-slot run (573.5 t/s) does not change the picture. The result is not an artefact of prefix caching.

Limits of this comparison

What could not be measured
  • FA off without f16 KV. A quantized value cache requires flash attention, and the engine refuses to start otherwise. Every FA-off arm therefore runs f16 KV, so its VRAM is not directly comparable with the FA-on arms.
  • DFlash with FA off at 256K context. Not buildable: at 131k it already peaks at 31.68 GiB of 31.86 GiB usable, so a 256K f16 window does not fit.
  • MTP and DFlash together. Not buildable on this engine build: the two draft types cannot share one speculative slot, and MTP alone does not serve this model without ngram-cache alongside it. No combined number exists, so none is shown.

How it was measured

Method

One model, one engine build, every arm identical except the accelerator flags: Qwen3.8-27B-Q4_K_M on llama.cpp Vulkan build 11517 (commit 8a1a9b512). Context window 131,072 tokens; KV cache q8_0/q4_0 for the FA-on arms and f16/f16 for the FA-off arms. Decode = 400 generated tokens per request on a chat-template-rendered prompt, measured from the server's own timings block; prefill = prompt processing on the same request. Short prompt 1,603 tokens, long prompt 27,722 tokens (varied blocks), temperature 0, seed 4242, cache_prompt:false on every measured request, warm-up request discarded. “Answers = baseline” compares six fixed prompts (arithmetic, list, code, three prose lengths) byte for byte against the baseline arm.

Decode at 27.7k context is measured on a deliberately repetitive stream (a one-word answer repeated), which is the best case for a speculative decoder: read the speculative arms' long-context decode as an upper bound. The two non-speculative arms are unaffected. VRAM is idle-after-load and peak-during-request, sampled during the measurement.

Method — the accelerator ablation

  • One variable at a time. A single model on a single engine build; each arm differs from the baseline only in the accelerator flags (flash attention on/off, and the speculative decoder: none, MTP, DFlash, MTP + ngram).
  • Same prompts, same settings. Temperature 0, seed 4242, cache_prompt:false on every measured request, warm-up discarded. Decode is 400 generated tokens per request on a chat-template-rendered prompt, read from the server's own timings block; prefill is prompt processing on that same request.
  • Two depths. A short prompt (1,603 tokens) and a long one (27,722 tokens, varied blocks). Decode at the long depth is measured on a deliberately repetitive stream — the best case for a speculative decoder, so read speculative long-context decode as an upper bound.
  • Answers compared byte for byte. Six fixed prompts (arithmetic, a list, a short function, three prose lengths) are diffed against the baseline arm, which is how “Answers = baseline” in the table is decided.
  • What could not be measured. FA off cannot run a quantized KV cache, so every FA-off arm uses f16 KV and its memory is not directly comparable. DFlash with FA off at 256K does not fit on the card. MTP and DFlash cannot share one speculative slot on this build, so no combined number exists.

Findings

  • Flash attention is a prefill multiplier, not a decode accelerator: with FA off, prefill at depth falls 83% (698 → 117 t/s) while decode barely moves (28.7 → 26.1 t/s).
  • The MTP + ngram production preset collapses at depth: 13.3 t/s decode against 73.9 t/s for MTP alone — 5.6× slower, and slower than plain MTP even at short context (61.3 vs 92.7 t/s).
  • Speculative decoding changes the long-form answer: 5 of 5 speculative arms failed to match the baseline byte for byte on the open-ended prose prompt (MTP, DFlash (n-max 7), DFlash (default n-max 3), MTP + ngram (production preset), DFlash with FA off), though they matched it on the short deterministic ones. Treat a spec-enabled result as a slightly different model, not the same model faster.
  • Flash attention also gates memory: the 2 FA-off arms of 7 must run f16 KV, which is why they need more VRAM at the same context.

About this table

Every row is folded from one or more raw SCHEMA-1 run records produced by the benchmark suite; the per-row records (raw records) are downloadable copies of the originals. Cells are percent correct on frozen prompt sets. The Decode / Prefill columns are pp512 (prefill) and tg128 (decode) tokens/s from llama-bench; the Server ctx / speed columns come from a live server: a cold request at temperature 0, cache_prompt:false, reading the server's own prompt_per_second and predicted_per_second. VRAM is the GPU's used-memory peak during the request. Videos are served from a CDN and only appear when the render exists. Every number here can be checked against the machine-readable dataset (data/results.json, plus the per-question chat JSONs); how each family of numbers is produced is in the method section below.

Method — the models table

  • Engine. llama.cpp llama-server, Vulkan backend, one model resident on the GPU at a time. Throughput is never measured while another model is loaded.
  • Builds. b11517 and b11517-8a1a9b512 and b11874. A newer build was needed for one newer architecture. A number is only comparable across rows measured on the same build.
  • Flags, per row: -ngl 99 -fa on -c <window> --jinja -np 1 -ctk q8_0 -ctv q4_0, plus -b 16384 -ub 2048 on the serving-shaped probes. -np 1 is one sequence slot: no batching, no concurrency.
  • KV cache: keys q8_0, values q4_0 on most runs; a few earlier runs used f16. The ablation block below measures what changing the KV type costs.
  • Speed columns. Prefill/Decode on a row are llama-bench pp512/tg128 with the weights loaded directly — no HTTP layer. The standard-probe columns are a server-side measurement of the same thing and will differ slightly; the two are labelled separately because they are not the same measurement.
  • Standard probe. A fixed filler document trimmed so /tokenize reports ~30,000 tokens (29,963–29,965 after templating) is sent once, cold: temperature 0, cache_prompt:false, no warm-up reuse. Decode is the server's predicted_per_second over a 64-token generation that ends on the length limit, not on an end-of-answer token; prefill is prompt_per_second for the same request.
  • Accuracy cells are percent correct on frozen prompt sets (GPQA, AIME, LiveBench, ~30K and ~110K embedded-context sets, tau2, Shell, TermBench), graded mechanically. A blank cell is not measured, never a failure.
