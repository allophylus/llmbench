Limits of this comparison

What this table does and does not say
  • One request per cell. Cold, uncached, no repeated runs — differences inside ±2% are run-to-run noise, which is why deltas are only coloured outside that band.
  • FA off cannot use the quantized KV cache. A quantized value cache requires flash attention, so every FA-off cell runs f16 keys and values; its VRAM is larger and its reachable context is shorter than the FA-on arms.
  • Cells marked “does not fit” are configurations whose server refused to start or could not allocate at that window: Qwen3.8-27B 256K.
  • MTP and DFlash are blank for Qwen3.6-35B-A3B because that file carries no MTP head and no drafter trained for it exists; the toggle does not apply, so no row is invented.
  • VRAM per rung is recorded in each cell's JSON and is not printed here: at a fixed rung it is a property of the model and KV type, not of the accelerator.
How it was measured

One model at a time on the same GPU, the same engine build (llama.cpp Vulkan build 11517 (commit 8a1a9b512)) and the same flags; only the toggled accelerator changes. For every cell the server is restarted with -c <rung>, then one prompt is calibrated with /tokenize to rung − 512 tokens: target context and client prompt length match. One cold /v1/chat/completions request follows (temperature 0, top_k 1, cache_prompt:false, ignore_eos:true, 64 generated tokens), and prefill/decode are the server's own timings.prompt_per_second / timings.predicted_per_second. KV cache q8_0 keys / q4_0 values on FA-on arms, f16/f16 on FA-off arms; one sequence slot (-np 1). The card's power cap was 250 W for every cell.

A number exists only if that request produced it. Servers that failed to start are recorded as failures with the engine's message, not as a low score.

About this table

Every row is folded from one or more raw SCHEMA-1 run records produced by the benchmark suite; the per-row records (raw records) are downloadable copies of the originals. Cells are percent correct on frozen prompt sets. The Decode / Prefill columns are pp512 (prefill) and tg128 (decode) tokens/s from llama-bench; the Server ctx / speed columns come from a live server: a cold request at temperature 0, cache_prompt:false, reading the server's own prompt_per_second and predicted_per_second. VRAM is the GPU's used-memory peak during the request. Videos are served from a CDN and only appear when the render exists. Every number here can be checked against the machine-readable dataset (data/results.json, plus the per-question chat JSONs); how each family of numbers is produced is in the method section below.

How every number on this site is produced, and what is deliberately not measured. Nothing here is inferred: if a request did not produce a value, the cell is blank.

Engine and build

  • Engine: llama.cpp llama-server, Vulkan backend on an AMD Radeon AI PRO R9700 (32 GiB). Models run on a different engine (e.g. a proprietary container format) are labelled with that engine in the table instead.
  • Builds: the build id is printed in the Speed evidence column of each row. Three builds appear: b11517, the mainline server that measured every early row; b11874, needed for one newer architecture; and b12110 (engine release v0.9.0), used for the gemma4 and nanbeige architectures and, after it matched b11517 in the build A/B below, for the serving configuration. A number is only comparable across rows measured on the same build.
  • Flags (one server at a time, recorded per row): -ngl 99 -fa on -c <window> --jinja -np 1 -ctk q8_0 -ctv q4_0, plus -b 16384 -ub 2048 on the serving-shaped probes. -np 1 means one sequence slot: no batching, no concurrency.
  • KV cache types: keys q8_0, values q4_0 on most suite runs; a few earlier runs used f16; the ablation block measures what changing the KV type does. The per-row value is in the evidence column.
  • Reasoning/thinking is off unless a tab says otherwise (enable_thinking:false via the chat template); the thinking tab is the on/off comparison.

Throughput: the standard probe

  • Prompt calibration. The probe uses a fixed filler document repeated and then trimmed so that /tokenize reports ~30,000 tokens (calibrated 29,953, actual 29,963–29,965 after templating). The same calibrated prompt is reused at every server window, so prefill at 32K and at 256K compare like with like.
  • Cold-probe policy. Temperature 0, cache_prompt:false, no warm-up reuse: every measured request pays the full prefill. A discarded warm-up request runs first when the server needs graph capture.
  • Decode. The server's own predicted_per_second over a 64-token generation that ends on the length limit, not on an end-of-answer token. /completion with ignore_eos is used where a model stops early.
  • Prefill is the server's prompt_per_second for the same request; VRAM is the GPU's peak used memory sampled during it.

The table's Decode / Prefill columns are a different measurement: llama-bench tg128/pp512 with the model loaded directly, no HTTP layer. That is why the two columns differ for the same model.

Browser games: how they are gated

  • One frozen prompt per game, temperature 0, max 8,000 tokens, up to three attempts; only a passing attempt is published.
  • A headless browser loads the page over http and file:// and checks: no console errors, canvas and a live WebGL context, three.js actually used at runtime, animation advancing between screenshots, keyboard input changing the scene, and a window.__game contract object being present and ready.
  • A robot then plays for 60 s with real keyboard events and records score, lives, survival and console errors. A score of zero with aligned aim means the game's collision geometry is broken — reported as a defect, not fixed.

What is NOT measured

  • Concurrency and batching. Everything runs one sequence per server (-np 1). No multi-user throughput, no batch-size sweep, no queueing latency.
  • Vision. Multimodal projector files are present for some models, but no image task is scored; vision is not benchmarked here.
  • Regression over time. Each row is a point-in-time measurement; there is no nightly re-run tracking drift, so a row from October is not a statement about today's speed on newer builds.
  • Memory over long sessions, thermal throttling at sustained load, and power-cap effects are only explored in the ablation block, not per model.
