Headline findings:

1. **The Q4_K_M depth result does not generalise — and that has a cause worth knowing.** In round 2,
   DFlash n7 looked like a short-context-only trick (103.8 → 56.1 t/s at depth). On the *same
   architecture* at Q4_0 it holds 90.0 t/s at 27.7k (2.0 % below MTP), and on DavidAU's MTP finetune
   88.0 t/s. Same drafter, same flags, same prompts — so the depth loss on Q4_K_M is a property of
   that quantisation/keep-set, not of DFlash. The published Q4_K_M row stands.
2. **MTP is the only arm that is good on every trunk that has it**: +2.6× to +2.9× at depth across
   Q4_K_M / Q4_0 / NEO-MAX / Huihui.
3. **FA is a prefill switch, not a decode switch, on every model** — decode is within noise at 1.6k
   everywhere (max spread 1.9 %), while prefill at 27.7k falls 83–86 % on the dense 27B models, 66 %
   on LFM3, and only 3–4 % on the two MoE-A3B models (they are prefill-bound on different kernels).
   FA-off also always costs VRAM because it forces f16 KV (see §3).
4. **ngram-cache (the prod preset's other half) is harmful at depth on every model that can run it**:
   Q4_K_M 74.2 → 10.8, Huihui 73.3 → 14.7; it only survives on Q4_0 (72.1 vs 79.6) and NEO-MAX
   (56.8 vs 65.4). It is never the best arm. (Fen's prod preset runs `draft-mtp,ngram-cache`.)
5. **Spec decoding changes greedy prose answers on every model** (§4) — 3/6 to 4/6 identical to
   baseline, never 6/6, on all six spec-capable builds.

## 3. Arrows that are not apples-to-apples

1. **FA-off cannot use the prod KV format.** `-fa off` + `--cache-type-v q4_0` aborts at load
   ("quantized V cache requires flash_attn to be enabled"), so every B arm runs f16/f16 KV. Peak
   VRAM difference is 6–9 GiB (e.g. Q4_K_M 20.6 → 28.9 GiB; NEO-MAX 22.4 → 30.7 GiB, i.e. 96 % of
   the 31.86 GiB card). NEO-MAX's FA-off run also spent 300 s in the 27k prefill retrying Vulkan
   allocations ("Failed to allocate pinned memory … ErrorOutOfDeviceMemory") — the numbers are real
   but that arm is at the memory edge, not a comfortable config.
2. **Quantisation differs between arms only by model.** Each arm uses the model's own gguf; the A3B
   rows are `UD-Q4_K_M` (unsloth dynamic quant), which is why they prefill at ~2.5k t/s while the
   dense 27Bs sit at ~700.
3. **LFM3 runs on a different build (b11874) and a different context (32k)** — b11517 never served it.
   Its long prompt is calibrated to 27,629 tokens rather than 27,475 (same ~27.7k target, its own
   tokenizer). Its 1.6k probe is 1,455 tokens rather than 1,603 for the same reason. So compare LFM3
   *within* its own group (A vs B); do not read its decode number against the Qwen columns as
   like-for-like.
4. **Qwen3.8-27B rows carry the vision mmproj** (as prod does); Ornith and LFM3 are text-only.
5. `--cache-reuse 256` is passed on every arm but llama.cpp disables reuse on any context that is
   multimodal or MTP-backed, so on several arms it is inert (journal says so; recorded per arm).

## 5. Integrity gates (why no row in the table is a crash dressed as a number)

Per arm, all must pass or the cell is VOID, logged with the reason, retried once:

1. `served_model_path` in `/props` == the gguf we launched (realpath compare)
2. `/props` `n_ctx` == the `-c` we passed
3. `NRestarts == 0` across load and measurement (a crash-looping unit also answers TCP briefly)
4. `/slots[*].speculative` == exactly the spec state the arm requested — **this gate is what caught two
   real defects in this run**: `--reasoning off` duplicated in argv made llama-server silently drop the
   speculative flags; and a leftover `z-gapclose.conf` drop-in (an `ExecStart=` with nothing after it)
   resurrected the unit's *original A3B* ExecStart, so "Qwen baseline" was briefly serving the 35B-A3B
   model at 64 t/s. `/props`' own `speculative.types` is **useless** here — it echoes the client
   sampling params and always reads `none`.
5. `predicted_n > 0` **and** a stop/truncated reason on both decode probes (~10 % of round-1 probes
   were 0-4 tokens and still reported a t/s)
6. 27k prompt within 27,000–28,500 tokens; all six answer runs `predicted_n > 0`, `cache_n == 0`
7. For spec arms: draft model present in the journal, accepted ≤ drafted tokens per request

Final status: **30 measured rows, 0 VOID, 0 not-applicable rows scored.** Every row in the main table
has a passing `arm-*.json` beside it.

## 6. Method

Server shape per arm (identical to round 2 except the model and the listed delta):

```
<b11517|b11874>/llama-server -m <model.gguf> [--mmproj <mmproj>]
  --host 127.0.0.1 --port 8080|8091  -c 131072|32768  -ngl 99  --jinja  -b 16384  -ub 2048
  --cache-type-k q8_0 --cache-type-v q4_0  --cache-reuse 256  --metrics --reasoning off
  -fa on|off  [--spec-type draft-mtp|draft-dflash[,ngram-cache] --spec-draft-n-max .. --spec-draft-n-min ..]
```

* **Arms**: A baseline `-fa on`, no spec — with **`--spec-type none` passed explicitly**. The flag is
  belt-and-braces: it makes "no spec" unconditional rather than dependent on what the build's default
  resolution does when a qwen35 trunk ships nextn tensors.
* **Spec flags used**: MTP `--spec-draft-n-max 7 --spec-draft-n-min 1`; DFlash default (n_max 3);
  D2 DFlash n7. E = `draft-mtp,ngram-cache` with n7.
* Launch via systemd user-unit drop-in per arm; `systemctl show -p ExecStart` is recorded and
  hard-gated (must be exactly one path, must name the model and the -c we set).
* Warm-up discarded; every measured request `cache_prompt:false`, `cache_n == 0`.
* VRAM = `mem_info_vram_used`, 4 Hz sampler, peak during the 27.7k request.
* Harness: `ablate3.py` (in this directory), driver `run-ablation3.sh`, state `state.json`
  (arm-level, resumable), all run under `screen` on the GPU host.
* Prod unit restored at the end to the preset that was live before the run
  (`z-active-model.conf` = `draft-mtp,ngram-cache` n4, `-c 131072`, on `active.gguf`), verified by a
  live 4-token completion afterwards.

## 7. Defects found and fixed during this round (kept, not hidden)

1. **Duplicate `--reasoning off`** (global list + per-arm list) → llama-server dropped every
   speculative flag without a hard error; the arm still produced plausible t/s. Fixed by emitting the
   pair once; gate 4 added.
2. **`z-gapclose.conf` drop-in poisoning** — `[Service] ExecStart=` with *no* value after it is a
   reset in systemd; coming from a later drop-in it also reset the unit to its *original* A3B
   `ExecStart`, so an arm launched the 35B-A3B model while the script believed it had launched Qwen.
   It was caught by the speed (64 t/s on a model that does 30) and by the journal naming a different
   gguf; `/props` alone still named our path, so the model-path gate alone would **not** have caught
   it. Fixed by parking every foreign `ExecStart=` drop-in for the run **and** hard-gating the
   effective `systemctl show -p ExecStart` to exactly one path naming our model and our `-c`.
3. **`/props speculative.types` is client-side only** — always `none`. Gate moved to `/slots`.
4. **LFM3 ran with thinking enabled** (its template defaults `enable_thinking=true`), which made the
   answer probes measure a reasoning stream and the long prompt misfire; fixed with
   `--chat-template-kwargs {"enable_thinking":false}` and a measured 27.6k prompt shape.
5. **LFM3's tokenizer is ~4× denser** on this filler than Qwen's (6.4k tokens per 30k chars); the
   generic greedy calibration kept landing at 25.8k tokens. Fixed with a measured fixed-shape prompt.
